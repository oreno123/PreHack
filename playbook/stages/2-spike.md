# 阶段 2 · 验证（Spike）

**目的**：用最小成本杀死不可行的题，或确认可行的题。

**输入**：每个候选题 + 它最脆弱的假设。

**输出**：每题一份 [spike 报告](../templates/spike-report.md)，结论 = 弃 / 改 / 进。

## 任务清单

1. 每题找出"最可能杀死这题的一个假设"（技术能通？数据能拿到？API 效果够好？）
2. 设计最小验证：一次 API 调用、一页静态原型、一个数据源探查——≤ 半天能做完的
3. 真跑。跑不通就换题或改题，不写全套代码
4. 写结论：弃（死因）/ 改（怎么改）/ 进
5. 胜出的题带着 spike 结论进阶段 3

## 退出条件

- 每题有真跑记录（命令、截图、返回值），纯纸面推演不算
- 弃题写明死因，防止后面反悔翻烧饼
- 幸存的题有明确结论

## 坑与检查点

- **先跑端点，不写全套**：spike 的目的是验证假设，不是提前开发
- 免费视觉 API 优先 glm-4v-flash（见 skills 速查与记忆 API 清单）
- 生图类验证用 `remote-batch-studio` 批量提交+评分，别手点

## 工具

- components: `remote-batch-studio`（批量生图+VLM 打分）
- skills: `mathmodel-pro`（数据可行性估算）
